## 1. 这份计划从你的实际起点出发

你现在是东华大学软件工程研一，本科网络工程；Python 还薄弱，但已在学 Transformer，87M 项目主要跟着开源代码或 AI 跑通，正在理解实现。你能平均每天投入 3–4 小时，愿意投入几千元租卡；可能 2027 S1 去墨尔本大学读 IT，约一年后申请正式研发实习，后续希望走大模型算法或 AI Infra。

我对你当前阶段的判断是：已经有模型训练的接触经验，独立编码、调试和实验解释能力还需要证据来确认。数学成绩说明你有学习基础，但不能直接替代推导与实验能力。近期无需重启一条几个月后才能碰模型的基础路线，也不能把“跟跑成功”直接按“熟练掌握”安排后续任务。

**推荐主线：理解并实现小模型 → 建立证据与任务评测 → 做可靠的单 Agent → 在同一任务上选择后训练或推理优化。**

Python、PyTorch、数学和工程基础嵌入这条主线。每阶段只精学一组必要工具，其余项目作为查阅材料。前六个月保留方向选择，后六个月将大部分专项时间投入一个方向。

你的一年目标可以具体表述为：能独立写、测、改一个小型 Transformer；能维护一个有数据、基线、失败分析的 Agent 项目；能拿出一份可信的模型效果或推理性能实验。达到这些标准后，优先申请 Python AI 应用研发、评测研发、模型工程实习，并用专项成果争取算法或 Infra 岗位。它是申请能力目标，不是录用保证。

## 3. 这一年只积累三个相互连接的成果

### 成果 A：小模型学习实验室

保留你的 87M 项目，以老师的 Lite 为对照，形成你能独立解释的缩小版。老师的 Lite 约 33M，集中在四个主要文件，包含现代 decoder 结构与 KV cache，适合接住你现在的学习。[SpongebobLite](https://github.com/Harris-Xie/SpongebobLite)

产物包括：模型实现、训练/验证、SFT、评测、运行配置、学习记录。87M 仍是学习与实验对象，不要求把它训练成通用好用的助手。后面的 Agent 可以调用合适的预训练模型或 API，两者不必强行绑成一个模型。

### 成果 B：有证据、有版本的技术声明核验 Agent

这是我为你选的主项目：**对一条技术声明查找证据，给出结论、来源位置、适用版本，证据不够时明确说明。**

例如输入“某版本的库是否支持某种功能”，系统从冻结的官方文档、README 和实验记录中检索，返回证据与版本。你学习模型与框架时，已经在不断接触这类问题；本科网络工程背景还能帮助你挑选网络、部署、并发和系统文档作为一个子领域。

老师 fork 的 CHEF 可用于学习“声明—证据—判断”任务及评价方式。它是 NAACL 2022 的中文事实核验数据集；你自己的技术文档集作为另一套任务，不能混合后冒充 CHEF 官方分数。[CHEF 原论文](https://aclanthology.org/2022.naacl-main.246/)、[上游仓库](https://github.com/THU-BPM/CHEF)

建议演进顺序：

1. 给定声明与证据，只做判定；先检查自己的标注标准是否清晰。
2. 在固定语料中检索证据，对比关键词/BM25、向量检索与精排。
3. 做固定的检索—阅读—判定工作流。
4. 加入单 Agent，让它决定是否再检索、读取全文或查询版本；设最大步数和费用上限。
5. 研究历史结论过期、证据相互冲突、工具超时等问题；根据失败再增加状态、记忆和恢复机制。

开始时用少量文本与 Markdown，避免同时引入 PDF、OCR、联网搜索和浏览器操作。需要复杂文档后再从 Docling/MinerU 选一个。先写 search/read/lookup_version 三个受限工具，保存 JSONL 轨迹；第 5–6 月再将一个工具接成 MCP。

它的个人特色来自持续维护的版本化任务集、清晰的错误分类和可复现改进；不是换个项目名字就能获得“独创性”。先用 30–50 个开发任务打磨规则，逐步扩到约 150–300 个认真检查的任务，另保留独立测试数据；数量是工作量参考，不是可靠性的充分条件。

### 成果 C：基于同一任务的一份专项实验

算法方向：研究数据质量、证据选择或工具调用 SFT，比较提示/工作流改进与训练的收益。

Infra 方向：将同一任务的模型服务部署起来，研究上下文长度、KV cache、批处理或缓存如何影响质量、延迟、吞吐和显存。

共同保留基线、配置、原始结果、失败样例与复现说明。最终可以是两个主要仓库、三份成果，不必拆成多个内容重复的简历项目。

## 5. 前八周：接着你现在的 Transformer 往下走

本表的周数是预算；某周难点需要两周很正常。模型模块按实际掌握顺序合并或调整。每周只有一个主要完成标准。

| 周 | 模型/项目线 | 当周补基础 | 完成标准 |
|---|---|---|---|
| 1 | 缩放点积注意力、causal mask、多头拆分（单头 → 多头）。**不把最小 decoder block 当作本周硬门槛** | 函数、类、模块、索引、调试；张量形状 | 不看参考代码重写 attention；说清每一步 shape；改变未来 token 不改变之前位置输出 |
| 2 | 拼最小 decoder block；embedding、残差、FFN、输出头；完成最小 LM forward；开始 RMSNorm/RoPE | broadcasting、reshape/transpose、nn.Module/Parameter | 输入 token 得到 [B,T,V]；能解释归一化和位置信息；与简单参考实现对照 |
| 3 | 完成 RoPE/RMSNorm/SwiGLU；GQA 放在基础 attention 正确后。若前面延期，GQA 可先理解并对照，降为 stretch | autograd、loss、optimizer；链式法则、softmax/CE | 用随机小输入查数值/梯度；参数确实参与优化；能解释 GQA 的头数关系 |
| 4 | next-token prediction；最小训练与验证循环；小样本过拟合 | Dataset/DataLoader、JSONL、文件读写、异常 | loss 下降且能过拟合很小的数据；解释 label shift 只应按实现做一次；保留独立验证样本 |
| 5 | 小模型短程预训练；数据切分、tokenizer/BPE 原理、学习率与 checkpoint | Git、环境锁定、命令行配置、日志；训练/验证/测试区别 | 从头运行可复现；恢复模型、optimizer、scheduler 和步数等状态；报告验证 loss |
| 6 | SFT template、assistant/response-only loss、padding | mask、-100、数据清洗脚本；理解 batch 差异 | 打印一条样本逐 token 监督范围；确认 prompt/padding 不计入预期 loss；解释特殊 token |
| 7 | C3/XCOPA 中选一套协议做简化 evaluator；复盘 87M 项目 | NumPy/pandas、accuracy、类别分布、随机/多数类基线 | 用手算样例检查 scorer；错误与真实零分分开；记录 prompt、选项计分和模型版本 |
| 8 | 一次小实验；补模块说明；尝试缓存/非缓存生成对照 | 控制变量、种子、结果表、bad case | 只改数据量或学习率等一个变量；用相同评测比较并解释局限；没有提升也如实记录 |

第八周的 KV cache 性能不是硬门槛；先做到输出对照，速度分析留到后面。DDP/FlashAttention/GRPO 不塞进这八周。

**第 1 周硬完成标准**只覆盖 causal single-head → multi-head attention。原来写在第 1 周的「拼最小 decoder block」移到第 2 周。这不是降低标准，而是保证第一周先走完一次「自己写 → 自检 → 对照 → 修正」。

**关于“手撕”的合理标准：**能够在空文件中实现核心算法并调通，不要求背下整个项目。需要查 PyTorch API 很正常。对 attention、loss mask、训练更新、scorer，先自己写再让 AI 指出问题；脚手架、重复数据处理和文档可以多用 AI，但要能解释最终行为。

每次练习采用：先口述输入输出与 shape → 写核心函数 → 用两三个边界例子检查 → 对照参考 → 修正 → 次日复写一个关键部分。AI 的第一轮帮助优先给线索，不直接给完整核心实现。

## 6. 基础线要学到什么程度

不是遇到报错才偶尔补语法：保留一份基础清单，每周集中补一个缺口，并让它在当前项目中被用到。

| 基础 | 前两个月 | 第 3–6 月 | 专项后补充 |
|---|---|---|---|
| Python | 函数、类、容器、迭代、模块、异常、文件、debug、类型 | dataclass/类型校验、生成器、HTTP 客户端、asyncio、pytest | 并发、性能、可维护接口；避免只会 notebook |
| PyTorch | tensor/shape、autograd、Module、loss、optimizer、DataLoader | 推理模式、dtype/device、保存恢复、显存与 profiler | 算法分支训练细节；Infra 分支算子、编译和分布式 |
| 数学/ML | 梯度、矩阵运算、softmax/CE、过拟合、验证集 | logistic regression、小 MLP、正则化、PR/F1、统计波动 | 算法分支再补 KL、偏好与策略梯度；Infra 分支补性能模型 |
| 工程 | Linux 命令、Git、环境、配置、日志 | SQL/SQLite、HTTP/FastAPI、超时重试、Docker、测试与 CI | Infra 补网络并发/调度/内存；平台方向按需任务队列 |
| 数据结构 | 数组、字符串、哈希、栈队列、复杂度 | 二分、双指针、树、堆、图、常见 DP | 复习解题思路、边界与复杂度，不追求只记题号 |

基础材料只各选一份：Python 用 [CS50P](https://cs50.harvard.edu/python/) 对应单元；PyTorch 用 [官方基础教程](https://docs.pytorch.org/tutorials/beginner/basics/intro.html)；ML 用 [scikit-learn MOOC](https://inria.github.io/scikit-learn-mooc/) 的数据划分/模型评价和 [动手学深度学习](https://zh.d2l.ai/) 的相关章节。已有明确短板再看对应视频，不同时从头刷四门课。

数据结构每周约三次、每次 30–45 分钟，归入基础时间；每周至少一次把题解关掉重写。第 3–4 月完成一个小型传统 ML 对照实验：例如在清楚定义的文本分类任务上比较简单特征+线性模型与一个神经模型，练数据划分与错误分析。这样不会只认识 LLM 名词而缺 ML 实验基础。

## 7. 第 3–6 月的项目验收

这四个月的重点是把“跑通”提升为“知道什么情况下有用、什么情况下失败”。

| 模块 | 最小实践 | 通过标准 |
|---|---|---|
| 数据 | CHEF 小样本理解；自己的技术声明集；文档版本与来源 | 标签含义和标注准则清楚；按文档/主题/时间隔离，避免相邻片段落入不同数据集造成泄漏 |
| 检索 | BM25 与向量检索；有必要再加 reranker | 报告 Recall@k/MRR 等检索指标，并人工核对证据支持程度；不把检索命中当结论正确 |
| 工作流 | 检索 → 阅读 → 输出结论和引用 | 能拒绝证据不足的任务；引用位置可以定位，处理过期和冲突证据 |
| Agent | 最多三个工具，有限步数，明确终止 | 与相同任务、相同模型的固定工作流比较；记录成功率、工具错误、token/费用、耗时 |
| 状态/记忆 | SQLite/JSONL 保存任务状态；先做简单摘要或检索 | 对比无记忆版本；验证旧结论更新和跨任务串扰，不默认“加记忆一定更好” |
| 工程 | FastAPI、类型校验、超时/重试、任务 ID、测试 | 工具参数错、检索为空、服务超时、模型输出不合格式都有清楚结果；用户输入与被检索文档不能任意改变工具权限 |
| 评测/观测 | 自己写 scorer 与逐样本记录，再接框架 | 看得出错误发生在哪一步；异常单独计数；LLM judge 与人工标注做过比较 |

公开旧 benchmark 可能进入过模型预训练；不能把高分完全归因于你训练或系统设计。冻结测试集后不用于调参；若发现评分错误，需要记录修订并对所有比较版本一致重跑。重复模型采样观察波动，但不能把对同一题重复采样当成新增独立题目。

| 用途 | 选择 | 深度与时点 |
|---|---|---|

| Agent 入门 | [Hello-Agents](https://github.com/datawhalechina/hello-agents) | 第 3–4 月选读当前版本的循环、工具、上下文与评测主题 |
| 小型源码 | [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent) | 手写循环后读执行、终止和轨迹；研究一个即可，核心类简短不等于完整系统只有百行 |

## 8. 第七个月如何选算法或 Infra

共同基础之后做两个短实验，选择过程也应有事实依据。

**训练试验：**选一个能在预算内运行的预训练小模型，对一项明确行为做少量 SFT，例如给定证据的结构化判定或工具参数生成。比较原模型、提示改进与 SFT；检查数据错误、过拟合和失败类型。先看模型卡、许可证、中文与工具能力、显存需求，实际开做时再确定具体型号，不把 2026 的模型名锁死一年。

**系统试验：**部署同一模型或合适的服务模型，固定请求集，对比不同输入长度、输出长度和并发；区分客户端、队列、prefill、decode 的延迟。测量前先做数值与结果正确性核对。

你如果愿意花更多时间改标注、看失败样本、推导训练目标，优先算法；如果更愿意追踪显存、等待、调度和算子耗时，优先 Infra。不要因为某一次结果更漂亮就决定；同时考虑导师资源与可获得的实习工作内容。

### 算法分支：第 8–10 月

顺序：数据与评测 → SFT/LoRA → 数据质量/数量对照 → 必要时偏好优化或可验证奖励 RL。

推荐课题从下面选一个：

- 在相同训练步数/预算下，筛选后的证据监督能否改善未见文档上的判断？
- 模型工具调用错误主要来自 schema、示例不足，还是任务分解？提示、工作流和 SFT 分别能解决多少？
- 更少、更准确的上下文能否同时改善成功率与费用？收益在长文档或冲突证据上是否成立？

交付：数据来源与处理、划分协议、原模型/提示/SFT 基线、至少一项消融、失败分析、训练配置与复现步骤。小样本差异应报告波动和样例，不追求预先承诺“提升 10%”。

RL 的进入条件：已经有能稳定执行的环境、可核验且难以被钻空子的反馈、可靠 SFT/工作流基线，还有训练时间预算。满足后只选 EasyR1 或 verl 一条路径研究 rollout→reward→update。事实判定不能随便用一个 LLM 的意见当无噪声真值；奖励增长必须对应独立任务成功率改善。

首年不强制完成 PPO、GRPO、DPO 全家桶，也不强制发论文。若希望冲研究型算法岗位，应尽早找到能指导实验的老师/研究团队，把问题、对照和复现做扎实，再讨论论文可行性。单靠更多框架项目难以替代研究证据。

### Infra 分支：第 8–10 月

先明确目标层次：AI 平台/可观测/资源管理、推理服务引擎、GPU kernel/编译器是不同岗位方向。使用 Docker 或启动 vLLM 只覆盖其中一部分。当前建议从**推理服务与性能分析**切入，再决定往底层走多远。

学习顺序：Linux/进程线程/并发 → CPU/GPU 内存与 tensor stride → profiler 和可靠计时 → prefill/decode、KV cache 与批处理 → 一项系统改进 → C++/Triton 基础。

课题优先选“相同文档前缀是否值得缓存”。固定模型、硬件、dtype、请求到达方式、输入输出长度与总任务集，比较冷/热缓存、不同前缀重复率和并发。记录 TTFT、token 间延迟、吞吐、显存、失败率；对 Agent 另报告整个任务耗时，不只测单次模型请求。

至少做几次独立重复；warmup、GPU 异步执行、服务队列、模型加载时间要单列或说明。统计尾延迟需要足够请求；样本很少时不把 P99 当稳定结论。SSE 消息块不是 tokenizer token，不能按块数报生成吞吐。优化不能靠减少实际输出或降低任务质量制造假收益。

按兴趣再做一个 Triton 向量加法或 softmax，包含数值对照和多尺寸 benchmark；能解释更快/更慢的原因后，再学矩阵乘和 attention。C++ 从 RAII、容器、引用/指针、内存和构建开始，不需要先把完整大仓库啃完。[Triton 官方教程](https://triton-lang.org/main/getting-started/tutorials/index.html)、[OSTEP 系统基础](https://pages.cs.wisc.edu/~remzi/OSTEP/)

DDP 先完成一个小模型的两卡一致性/梯度同步实验，理解通信和随机性；FSDP、TP/PP、分离部署、MoE 通信作为之后的扩展。本科网络工程经历可以帮助你理解通信路径，但是否掌握仍以实验解释为准。

## 9. 哪些内容更值得为 2027 年准备

下面是基于当前项目变化与工程问题的判断，不能保证未来岗位数量或某个框架的流行度。

| 优先能力 | 为什么在你的计划中优先 | 对应证据 |
|---|---|---|
| 评测与数据质量 | 无论换什么模型，都需要判断改动是否有效 | 有独立测试集、逐样本结果、错误与波动说明 |
| Agent 的执行与状态 | 多步系统会发生错误、超时、上下文膨胀 | 轨迹回放、预算限制、恢复和明确工具边界 |
| 上下文与证据管理 | 更多上下文会影响费用、速度和信息质量 | 检索/摘要/版本策略在同任务上的对照 |
| 后训练的问题定义 | 训练价值依赖数据与目标，不能仅靠 API 熟练 | 原模型/提示/SFT 对比，独立测试不泄漏 |
| 推理性能与资源意识 | 算法与应用最终都受显存、延迟和成本约束 | 同口径性能实验与 profiler 证据 |
| 源码阅读与工程协作 | 能解释并修改一个模块，比罗列集成更可审查 | 小修改、边界测试、清楚文档和真实贡献 |

每周最多用约半小时浏览动态；每月挑一篇与你当前失败问题相关的论文认真读，基础阶段可以更少。固定代码和依赖版本，阶段结束再评估升级，不跟着所有新版本迁移。机器人、全双工语音、多模态 GUI、MoE、大规模 RL 都有价值，但今年不同时开线。

项目状态变化也说明路线应围绕能力组织：Swarm 已被后继 SDK 替代，AutoGen 与 GraphRAG 有维护模式说明，LLM Guard 已归档；旧名字仍能讲历史思想，但不能照截图直接指定未来一年主依赖。[Swarm](https://github.com/openai/swarm)、[AutoGen](https://github.com/microsoft/autogen)、[GraphRAG](https://github.com/microsoft/graphrag)、[LLM Guard](https://github.com/protectai/llm-guard)

### 每天约 3.5 小时的模板

### 示例预算：总计 3,000 元

这是可调整的支出计划，不是 AutoDL 实时报价，也不是立即租卡方案。

| 用途 | 额度 |

对你投递优先级的建议：

1. Python AI 应用研发、模型工程、偏代码与实验的评测研发，与前六个月成果最接近。
2. 有明确后训练成果后，申请应用算法、数据/评测算法和后训练相关实习。

简历现在应如实区分“开源复现”“本人实现”“实际训练/评测”。后续描述使用问题、本人工作、测试协议与真实结果；没有独立完成的 DDP/GRPO 或未经验证的数值，不写成自己的成果。老师仓库只有三个被标记为 fork，也不意味着其余代码可以默认都算你的原创。

## 13. 下一次学习从这里开始

从你正在学的 attention 开始，准备一个空文件和一小组固定 tensor。先实现单头因果注意力，口述 Q/K/V 的 shape、缩放和 mask；检查未来位置不能影响过去，再扩到多头。如果卡在 class、reshape 或 broadcasting，就补对应知识点，完成当前函数后再对照 Lite。

这一周的完成标志是自己能写、能检查、能解释这一个模块。暂时不用安装 Agent 框架、购买大额算力或重写网站外观。
